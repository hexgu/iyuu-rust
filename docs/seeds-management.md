# 种子管理：从「辅种记录」到「主种子 + 辅种子」

本文是「辅种记录」页面的产品设计重构说明，同时是实现的契约文档。后端分组逻辑、
API 形状、前端页面结构都以本文为准。

## 1. 为什么要改

旧页面是一张**流水账**：一行 = 一次辅种尝试（源 hash → 目标 hash）。它回答的是
「工具干过什么」，而不是「现在我的种子是什么状态」。用户真正要管的是**一个资源**：
它在主站做种，是否已经在其它站点也铺开、哪一个站失败了。流水账把同一资源的多条记录
打散在时间轴上，用户得自己在脑子里做聚合。

所以页面的主语从「尝试」换成「种子组」：

```
种子组 = 主种子（数据来源，本地实际下载的那一份）
       + 辅种子（其它站点上同一份数据的种子，按站点折叠在下面）
```

## 2. 怎么算「同一个种子」

这是重构的核心。三个层次，从强到弱：

| 层次 | 依据 | 用途 |
| --- | --- | --- |
| 精确身份 | `info_hash`（小写十六进制） | 同一个 .torrent。哈希相同就是同一条，无需任何推断 |
| 数据身份 | `total_size` 完全相等 + 名称归一化后相符 | 同一份数据在**不同站点**上的不同 .torrent（哈希必然不同）。这是跨站识别的主依据 |
| 位置身份 | `save_path` + `content_path` | 交叉验证，也用于在下载器里定位实际文件 |

判定规则（`crates/core/src/identity.rs`）：

1. 大小不同 → **一定不是**同一个资源。这是一条硬否定，先把候选砍掉一个数量级。
2. 大小相同，名称归一化后相等 → 同一个资源。
3. 大小相同，名称归一化后不相等 → 比较词元集合的 Jaccard 相似度，`>= 0.85` 视为
   同名。这一步专门对付站点的改名习惯：中文名方括号前缀 `[律界战争].`、
   `【】` 包裹、`WEB-DL` / `WEB.DL` 分隔符差异、尾部的组名标注。
4. 大小未知（0）时不做名称推断——宁可分成两组，也不能把两个不同的资源并成一组，
   因为合并会直接误导用户去删错种子。

名称归一化（`name_key`）：小写 → 去掉开头的 `[...]` / `【...】` 中文名段（站点各自
加，不可靠）→ 标点统一成空格 → 压缩空白。词元相似度在此基础上做集合运算。

## 3. 分组算法

对「下载器里的种子」和「辅种记录」建并查集：

- 每条辅种记录连一条边：`source_hash ↔ target_info_hash`。这条边来自工具自己的
  事实记录，优先级最高——它明确说了「这份数据是从哪个种子复用的」。
- 下载器里同数据身份的两个种子连一条边（按大小分桶，桶内再比名称，避免 O(n²)）。
- 主种子已经被删、只剩辅种记录时，组照样存在：它的成员是记录，不是下载器条目。

只列出**参与辅种**的组：组内至少有一条辅种记录，或组内有带 `iyuu-reseed`（含
`iyuu-reseed:<site>` / `iyuu-reseed:verified`）标签的种子。纯下载器种子归「下载器」
页，不在这里重复出现。

### 主种子的判定顺序

1. 组内、在下载器里、已完成、**没有**辅种标签、且不是任何一条辅种记录的目标 →
   这就是用户自己下的那一份。
2. 退一步：在下载器里、已完成、不是任何记录的目标。
3. 都不存在（主种子被删了）→ 用辅种记录里保存的 `source_name` / `save_path` 做快照，
   组状态标记为 `main_missing`。**不会**退而把某个站点的辅种子标成「主种子」：
   那会让用户以为本地还有原件，而实际上他手上只剩几份跨站副本。
4. 只有标签、没有任何辅种记录时（工具加过、但记录被清掉了），才按「在下载器里、
   已完成、加入最早」挑一个当主种子 —— 这时候组里也没有别的候选。

剩下既不是主种子、也不是辅种目标的下载器条目，作为 `duplicates` 返回：它们是同一份
数据的多余副本（重复下载、重复添加）。UI 只提示数量，不提供自动处理。

### 组状态

| 状态 | 含义 |
| --- | --- |
| `healthy` | 主种子在、所有辅种子都已校验通过在做种 |
| `verifying` | 有辅种子正在校验（`added` / `verifying` / 下载器在 checking） |
| `degraded` | 有辅种子失败（`verify_failed` / `missing_files` / `fetch_failed` / `add_failed` / `timed_out`，或下载器报错/文件缺失） |
| `main_missing` | 主种子已不在下载器，只剩辅种记录 |
| `no_aux` | 主种子在，但一个辅种子都没有 |

判定优先级：`main_missing` > `degraded` > `verifying` > `no_aux` > `healthy`。
主种子缺失要先说，因为它意味着数据可能已经不在本地。

「还在下载器里、但下载器报文件缺失 / 错误」的主种子**不算** `main_missing`，而是
`degraded` + `main.present=true`。两者要分开：一个是去找回一个被删掉的种子，一个是
去修一份还在的种子，处理动作完全不同。

## 4. API 契约

### `GET /api/seeds`

查询参数：`filter`（`all` / `has_failure` / `verifying` / `no_aux` / `main_missing`）、
`q`（名称 / hash / 站点 / 路径 子串匹配）、`limit`（默认 50，上限 200）、`offset`。

```jsonc
{
  "total": 12,          // 命中过滤条件的组数
  "limit": 50,
  "offset": 0,
  "counts": {           // 不受 filter 影响，永远是全量统计
    "groups": 12, "aux_total": 30, "aux_seeding": 22,
    "aux_verifying": 3, "aux_failed": 5,
    "with_failure": 4, "no_aux": 2, "main_missing": 1
  },
  "items": [{
    "key": "c4ee…",              // 组标识：主种子 hash；主种子缺失时取组内最小 hash
    "name": "…", "size": 6661586546, "save_path": "/data/…",
    "category": "刷流",
    "state": "healthy",
    "main": {                     // 主种子快照，可能 present=false
      "hash": "…", "name": "…", "size": 0, "save_path": "…",
      "state": "stalledUP", "phase": "complete", "progress": 1.0,
      "seeding_time": 3600, "uploaded": 1024, "ratio": 1.0,
      "added_on": "2026-11-13T…", "tags": [], "trackers": [], "present": true
    },
    "aux": [{
      "attempt_id": 7, "site": "springsunday", "site_name": "春天",
      "sid": 23, "torrent_id": 12345, "info_hash": "…",
      "state": "seeding", "check_count": 2,
      "added_at": "…", "last_checked_at": "…", "finished_at": null,
      "message": "校验通过，开始辅种",
      "in_downloader": true,
      "live": { "state": "stalledUP", "phase": "complete", "progress": 1.0,
                "seeding_time": 100, "uploaded": 0, "ratio": 0.0, "added_on": "…" }
    }],
    "duplicates": [{ "hash": "…", "name": "…", "uploaded": 0, "added_on": "…" }],
    "counts": { "aux": 2, "seeding": 2, "verifying": 0, "failed": 0 },
    "updated_at": "…"
  }]
}
```

排序：组状态优先级（`main_missing` → `degraded` → `verifying` → `no_aux` → `healthy`），
同状态内按 `updated_at` 倒序。

### 动作接口

辅种动作沿用记录 id，前端从 `aux[].attempt_id` 取：

- `POST /api/attempts/{id}/requeue` — 重新校验
- `DELETE /api/attempts/{id}` — 删除这条辅种记录（不碰下载器里的种子）

## 5. 页面结构

路由 `/seeds`，导航名「种子管理」；`/attempts` 保留为重定向，旧书签不会 404。

```
种子管理                                    [搜索名称/站点/hash]
12 组 · 辅种 22/30 成功 · 3 校验中 · 5 失败
[全部] [有失败] [校验中] [无辅种] [主种子缺失]

▸ 律界战争 S01 …            2160p · 6.2 GB   春天      ● 2/3   3 分钟前
▾ 玫瑰战争 S01 …            1080p · 1.1 GB   M-Team    ● 3/3   刚刚
    春天      seeding    a27d…   2 次   上传 0 B     [重新校验] [删除]
    OpenCD    verify_failed f3b1… 5 次  保存路径不一致 [重新校验] [删除]
```

- 行首箭头展开 / 收起辅种子子列表（默认收起，展开状态在会话内保留）。
- 主行：名称、大小、主站（取主种子第一个 tracker 的 host）、组状态、辅种进度
  `成功/总数`、更新时间。
- 子行：站点、状态徽标、目标 hash 短写、校验次数、上传量、失败原因、行内动作。
- 有失败 / 主种子缺失的组，行首给一个红点提示，不用展开也能看见。
- 校验中的组每 5 秒自动刷新；没有在途校验时不轮询。
- 状态说明卡片保留（校验通过才算成功这句话得留着）。

## 6. 不做的事

- 不在这个页面直接操作下载器（删除种子、改路径）——那是「下载器」页和 qB 自己的事，
  这里只管理辅种关系的记录与重试。
- 不引入新的持久化表：分组是从「下载器快照 + 辅种记录」推出来的，写死一份组表反而会
  在下载器状态变化后变成谎言。
- 不做自动合并同名组的人工「合并 / 拆分」操作；识别错了先修 `identity.rs` 的规则。
