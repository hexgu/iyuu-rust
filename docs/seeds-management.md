# 种子管理：以「下载器」为主语

本文是「种子管理」页面的产品设计与实现契约。上一版把页面主语定成「一份数据 + 它的
辅种」，方向对了一半：**页面管的是下载器里的种子，只是按「同一份资源」聚合成行。**

## 1. 主语：下载器，不是辅种记录

旧页面的错误在于从「辅种记录」出发：只列出参与过辅种的组。于是

- 用户自己下的一份种子，没人给它配过辅种，就永远不出现在「种子管理」里；
- 用 Hermes / MoviePilot / 手工加的副本，没有我们库里的记录，看起来像不存在；
- 删掉一条记录，页面上整组就消失，可下载器里的种子明明还在。

真实的所有权顺序是：

```
下载器（种子的事实来源）
  └── 资源组 = 指向同一份数据的种子集合
        ├── 主种子：用户自己下的那一份，行上展示
        └── 辅种：其它站点上的副本，折叠在下面
```

所以页面默认列出**下载器里的全部种子组**，主种子一行，辅种折叠。纯下载器种子也是
合法的组（`no_aux`）——它就在那儿，用户有权看见它有没有铺开。

记录（`reseed_attempts`）是**元数据**，不是主语：有就补上站点、校验次数、失败原因，
没有也不影响种子出现在页面上。

## 2. 识别：证据链，不是标签

标签是用户随手就能改的东西，也是别的工具各写各的。用它当唯一识别依据，等于把页面的
正确性交给一个可变的字符串。新的识别顺序按**证据强度**排：

| 顺序 | 证据 | 强度 | 说明 |
| --- | --- | --- | --- |
| 1 | `content_path`（缺失时 `save_path + name`）+ 大小一致 | 硬正 | 同一份数据在磁盘上只有一个落脚点。路径相同、大小也相同就是同一份数据，与站点、标签无关 |
| 2 | `total_size` 相等 + 名称归一化/Jaccard ≥ 0.85 | 正 | 路径不同的副本（不同盘、不同挂载点）靠这个对齐 |
| 3 | 辅种记录 `source_hash ↔ target_info_hash` | 正 | 工具自己干过的事实 |
| 4 | 标签（`iyuu-rust` / `辅种` / 旧 `iyuu-reseed*`） | 提示 | **只用来判断角色**，不用来判断是不是同一个资源 |
| 5 | `total_size` 不等 | 硬否 | 大小不同一定不是同一份数据 |

第 1 条是这次改动的关键：它让「Hermes 加的、没有任何记录的副本」和主种子自动落到同一个
组里，因为跨站辅种复用的本来就是同一批文件。第 2 条兜底那些复制到别的盘做种的场景。
标签降级成第 4 条，只回答「这个种子像不像辅种」——而且答错也只会影响角色，不会把一个
资源劈成两半。

角色还有一条很硬的证据：**下载流量**。主种子是用户真的在这里拉过数据的那一份；辅种是
复用磁盘上已有的文件加进来的，客户端的 `downloaded` 是 0。它比标签可靠——标签是人打的，
流量是客户端记的账。失效场景也有：副本校验失败后重新下载过整份数据、主种子是从别的
客户端导入的（统计被重置）。所以它排在辅助种记录之后、标签之前。

`name_key` / `same_release` 的规则不变（见 `crates/core/src/identity.rs`）：去掉站点自加
的 `[中文名].` / `【…】` 前缀、标点归一、词元 Jaccard 阈值 85%；大小未知不做名称推断。

## 3. 角色判定与「依据」

组内选主种子，按顺序：

1. 有辅种记录指名它是 `source_hash` → 主种子，依据 `record`。
2. 组里只有一个活种子，且它不是记录的目标、也没带辅种标签 → 主种子，依据 `single`。
3. 剩下的候选里，排除「记录的目标」与「带辅种标签」的，按「有下载流量 → 校验通过 →
   加入更早 → 上传更多」取第一个 → 依据 `record`（有记录时）、`tag`（靠标签排除出来的）
   或 `traffic`（靠下载量认出来的）。
4. 没有记录、没有标签、也都没下载过数据，组里就是多个同数据副本 → 取最早加入的完成
   种子，依据 `inferred`。这一条是推断，UI 会把它标出来，不假装是事实。
5. 组里全是辅种（都带标签或是记录目标）→ 主种子已被删除，`main_missing`；名称/路径用
   记录里的 `source_name` / `save_path` 做快照。**绝不**把某个站点的副本冒充成主种子。

依据随组返回（`main_source`），页面在展开区显示「识别依据」。识别错了先修规则，不要
让用户手工纠正。

辅助种子则取「组内除主种子之外的所有活种子」+「记录里存在但下载器里已经没有的目标」：

- 活种子的站点：记录里有就用记录，没有则取 tracker host；再没有就是未知。**不读标签里的
  站点名**——标签已经不区分站点了。
- 记录里的失败目标（`verify_failed` / `add_failed` …）即使种子不在下载器，也要显示，
  否则用户看不到「这个站没辅上」。
- 同一个组里同一个站点出现多份，或者某份活副本既没有记录也没有辅种标签 → 标记
  `duplicate`（同数据的额外副本）。

## 4. 组状态

| 状态 | 含义 |
| --- | --- |
| `main_missing` | 主种子已不在下载器，只剩辅种 |
| `degraded` | 主种子报错/文件缺失，或有辅种失败、或记录说成功但种子已不在下载器 |
| `verifying` | 有辅种或主种子正在校验 |
| `no_aux` | 主种子在，一个辅种都没有 |
| `healthy` | 主种子在，辅种全部校验通过且在种 |

优先级 `main_missing` > `degraded` > `verifying` > `no_aux` > `healthy`。

「记录说 `seeding`、下载器里找不到」算 `missing`，计入失败：只承认真的在做种。

## 5. 标签策略

- 我们自己只打 `iyuu-rust`，**不带站点后缀**。站点信息从 tracker / 记录里来，不从标签里
  解读。
- 识别为辅种的标签 = `iyuu-rust` + 旧 `iyuu-reseed` / `iyuu-reseed:*` + 用户配置的
  「其它辅种工具的标签」（`reseed.aux_tags`，默认 `辅种`）。
- `POST /api/seeds/tags/rewrite` 把旧的 `iyuu-reseed*` 重写成 `iyuu-rust`：先移除旧标签，
  再添加新标签。客户端不支持移除标签时（如 Transmission 的 label 语义），该种子会被跳过
  并计入 `skipped`，不谎报成功。
- 引擎不再写 `iyuu-reseed:verified`：校验结果在库里，标签不是账本。

## 6. IYUU 查询：每个资源只问一次

IYUU 的 `/reseed/index/index` 是按 info hash 查的，一次查询就能把该资源在所有站点的
候选一起返回。同一份数据在 A 站、B 站上是两个 hash，把辅种副本也拿去查，等于拿同一份
数据重复消耗额度，答案还完全一样。

所以查询前先按第 2 节的规则去重，每个资源只留一个代表（`crates/core/src/group.rs`），
代表优先选「辅种记录里当过来源的 → 没被标成辅种 → 校验通过 → 加入更早 → 上传更多」。
第一条来自 `attempts.source_hash` 的历史，能让「重新添加过的主种子」不被更早的副本
抢走代表位。查询日志里的
「扫描完成」会给出「种子数 → 资源数」，能直接看出省下了多少次请求。

## 7. API

### `GET /api/seeds`

`filter`：`all` / `has_aux` / `no_aux` / `has_failure` / `verifying` / `main_missing` /
`inferred`；`q`：名称 / hash / 站点 / 路径 / 标签；`limit`（默认 50，上限 200）；`offset`。

```jsonc
{
  "total": 320,
  "counts": {
    "groups": 320, "torrents": 412,
    "with_aux": 92, "no_aux": 226,
    "aux_total": 104, "aux_seeding": 88, "aux_verifying": 3, "aux_failed": 13,
    "aux_missing": 8, "main_missing": 2, "with_failure": 11, "inferred": 4
  },
  "items": [{
    "key": "c4ee…",
    "name": "…", "size": 6661586546,
    "save_path": "/data/…", "content_path": "/data/…/…",
    "category": "刷流",
    "state": "healthy",
    "main_source": "record",       // record | single | tag | traffic | inferred | snapshot
    "main": { "hash": "…", "present": true, "downloader": "qBittorrent",
              "downloaded": 6661586546, "…": "…" },
    "aux": [{
      "attempt_id": 7,            // 可为 null：别的工具加的副本，库里没有记录
      "info_hash": "…", "site": "springsunday", "site_name": "春天",
      "site_source": "record",     // record | tracker | unknown
      "origin": "record",          // record | tag | content
      "duplicate": false,
      "state": "seeding",         // seeding | verifying | failed | pending | missing
      "in_downloader": true, "tags": ["iyuu-rust"],
      "phase": "complete", "progress": 1.0,
      "uploaded": 0, "ratio": 0.0
    }],
    "counts": { "aux": 2, "seeding": 2, "verifying": 0, "failed": 0 },
    "updated_at": "…"
  }]
}
```

排序：状态优先级 → `updated_at` 倒序 → 名称。

### 动作

- `POST /api/attempts/{id}/requeue` — 重新校验（只有带记录的辅种有）
- `DELETE /api/attempts/{id}` — 删记录（不碰下载器；种子还在，行也还在）
- `POST /api/seeds/tags/rewrite` — 旧标签重写，返回
  `{ scanned, matched, rewritten, skipped, client }`
- `POST /api/seeds/cleanup?dry_run=true|false` — 自动清理，默认只预览
- `GET /api/seeds/cleanup` — 最近 50 条清理审计

- 默认只展示主种子；辅种子折叠，展开状态在会话内保留。
- 没有辅种的组不显示箭头，也不允许展开。
- 展开区写「识别依据」：记录 / 唯一候选 / 标签 / 下载流量 / 推断，`inferred` 的组可筛选。
- 校验中的组每 5 秒刷新；没有在途校验不轮询。
- 标签不再是站点信息的来源，只在辅种行里作为「谁打的标记」展示。

## 9. 自动清理

主种子被删掉之后，铺在别的站点的副本就没有意义了：占硬盘、占客户端槽位，还让
「主种子缺失」一直挂在页面上。`cleanup.enabled` 打开后，每次任务结束都会跑一遍，
也可以在页面上手动预览 + 执行。

规则，按重要性排序：

1. 只处理 `main_missing` 的组——主种子不在下载器里。
2. **必须有证据**：组内有辅种记录，或者组内所有活种子都带辅种标签。靠推断识别的组
   一律不动，只在页面上展示。这里有个前提：主种子确实在这个下载器里管过。如果原件
   在另一个客户端（当前还不支持多下载器），一个「全部带辅种标签」的组会被当成主种子
   缺失——这是这条规则目前的盲区，靠「默认关闭 + 先在页面上预览」来兜。
3. **不做延迟观察**：确认缺失且有证据，下一次任务就清。排期等待会让人误以为已经
   清过了，而实际上只是在耗时间。
4. 种子通过下载器删，`cleanup.delete_files` 决定连不连文件（主种子删了但文件留下时，
   这是唯一会收掉那份数据的地方）。删文件前会检查有没有别的资源组的种子落在同一个
   目录里（比如季包目录里的单集）——有就只删种子、不删文件。库里只剩记录、没有任何
   活种子时只清记录，**不去猜宿主机的路径删文件**：应用看不到宿主机目录，猜错了
   就是删别人的数据。
5. 每次动手都写 `cleanup_log`（hash、站点、有没有删文件、是不是 dry-run）。
6. 接口：`POST /api/seeds/cleanup`（默认 `dry_run=true`，要真删必须显式传 false）、
   `GET /api/seeds/cleanup` 回看最近 50 条审计。

## 10. 边界

- 分组仍是**推导**出来的，不落库：下载器一变，下一次请求就是新结果。
- 记录只补元数据，不决定种子是否存在。
- 多下载器：当前配置只连接一个下载器实例；组的每条记录都带 `downloader` 名称。接入
  第二个实例时**先按下载器分区再分组**——不同机器上的 `/data/x` 不是同一个位置，
  跨机合并会把两份数据认成一份。识别逻辑本身不用改。
- 识别错了先修 `identity.rs` 的规则，不做手工合并/拆分。
